# Polar LOLA horizon workflow

`node scripts/run-polar-analysis.mjs` builds a terrain horizon from the locally installed `LDEM_80S_80M` polar product, registers that horizon to a time-series request, runs the registered sky generator, and computes visibility. The runner requires `data/polar-lola-manifest.json` and `scripts/polar-lola.py` (CLI over `src/features/visibility/polar_lola.py`); missing data or an unavailable generator is an error, never a flat-horizon fallback. Install dependencies with `python -m pip install -r scripts/requirements-registration.txt -r scripts/requirements-polar.txt`, then retrieve official PDS image and label with `python scripts/fetch-polar-lola.py`. Fetcher caps transfer at 30,000,000 bytes; JP2 expected size is 29,837,992 bytes. Manifest records locally calculated SHA-256 values; these are not publisher checksums.

Defaults match the registered analysis example: Shackleton reference example, latitude −89.9°, longitude 0°, observer height 2 m, three UTC samples starting `2026-11-14T00:00:00Z` at five-minute intervals. Horizon defaults are 5° azimuth spacing, 80 m distance spacing, and 200,000 m maximum range. At the default 5° bearing interval, widening radial step from 80 m to 240 m changed sampled maximum horizon elevations by up to 0.44558056° in a measured run; keep 80 m default. Runtime limit caps azimuth×range samples at 200,000. A measured default 80 m / 5° generation used about 208 MiB peak Python working memory and about 922 MiB peak private commit; 64 MiB GDAL cache limit is only one component, not a total-process memory cap. See [coordinator measurements](research/coordinator-polar-validation.md) for details; reproduce Windows terrain-process memory probe with `python scripts/measure-polar-memory.py`. Backend/UI remain separate from this CLI. For example:

```sh
node scripts/run-polar-analysis.mjs --site-id Shackleton-reference-example --lat -89.9 --lon 0 --height 2 --start 2026-11-14T00:00:00Z --count 3 --step-minutes 5 --azimuth-step 5 --distance-step 80 --max-distance 200000
```

The longitude is normalized to [−180°, 180°). Exactly ±90° latitude is rejected because local azimuth has no unique north direction at the pole. The generator's `provenance.surfaceHeightM` is authoritative for the request; callers cannot set it. Its source SHA-256 and product identity are carried through registration and checked against the real terrain document. Before Python runs, runner checks trusted product/version/dataset/official URLs, retrieval records, fixed product byte count, and SHA-256 of both local source files against download manifest. CLI accepts `--python` to select Python executable and `--kernels` to select registered-sky kernel directory. Both Python processes have a 120-second timeout and share a temporary request/output directory; temporary files are removed afterward. Temporary files use the OS temp directory on Linux/macOS; Windows uses `%LOCALAPPDATA%\Temp\opencode` (or an existing `%TEMP%` when it already points there). Output is `output/polar-analysis.json` unless `--output` selects another path.

LDEM_80S_80M denotes nominal grid spacing, not height accuracy, hazard-scale detail, or proof that every grid cell is an independent laser shot. Even an 80 m ray step is a sampling choice, not a guarantee that narrow ridges are captured. A measured 5° run changed maximum sampled horizon elevation by up to 0.44558056° when radial step widened from 80 m to 240 m. The 5° angular spacing also leaves bearings between rays unsampled. The 200 km cutoff excludes more distant terrain; report the actual generator coverage and any NoData/coverage warnings with results. This calculation does not establish landing safety, panel power, or communications sufficiency. It does not integrate QuickMap/Moon Trek visual inspection or itself retrieve Horizons data. A missing/invalid polar product, uncovered ray path, or registration mismatch must stop the analysis rather than silently substitute synthetic terrain.
